# DevERP Specification

Complete, free, open-source ERP for a software / IT services company.
This file is the source of truth for **what** to build. `PROGRESS.md` tracks **what is done and what is next**. `AGENTS.md` holds the working rules.

Status legend: **[DONE]** built in Phases 1-3 and committed. **[TODO]** not built yet. **[VERIFY]** may already exist; check the repo before building.

---

## 1. Hard constraints

- 100% free and open source. No paid APIs, no paid SaaS, no credit-card-gated services.
- No payment gateways (payments are recorded manually), no SMS providers, no requirement for Redis.
- Must run locally with one command: `docker compose up`. Must also run without Docker on SQLite for development.
- All configuration through environment variables, documented in `.env.example`.
- No placeholders, TODOs, stubbed logic, or fake data in delivered features. Every feature works end to end.
- Email: console backend in development, SMTP through environment variables in production. The app must be fully usable with email disabled (in-app notifications always work).

## 2. Tech stack (fixed)

| Layer | Choice |
|---|---|
| Backend | Python 3.12, Django 5.2, Django REST Framework, drf-spectacular, django-filter, simplejwt, django-allauth, django-otp (TOTP 2FA) |
| Database | SQLite (dev), PostgreSQL (production), configured with dj-database-url |
| Background jobs | django-q2 with the ORM broker (no Redis) |
| Realtime | Polling or Server-Sent Events (no Channels/Redis) |
| Frontend | React 18, Vite, TypeScript (strict), Tailwind CSS, TanStack Query, React Router, react-hook-form, zod, Recharts |
| PDFs | WeasyPrint (invoices, quotes, payslips, reports) |
| Spreadsheets | openpyxl (Excel), csv (CSV) |
| Search | PostgreSQL full-text search, `icontains` fallback on SQLite |
| Analytics / ML | pandas, scikit-learn |
| Static files | whitenoise |
| Quality | pytest + pytest-django + factory_boy, ruff, mypy, eslint, vitest, GitHub Actions CI |

## 3. Architecture rules

### 3.1 Repository layout

```
backend/
  config/            settings (base/development/production), urls.py, q cluster config
  apps/
    core/            users, roles, RBAC, audit, notifications, settings, search, auth
    hr/              departments, employees, attendance, leave, payroll, recruitment ...
    projects/        clients, projects, tasks, sprints, timesheets, allocation ...
    crm/             leads, contacts, deals, quotes                          [TODO]
    finance/         billing, invoices, payments, expenses, ledger           [TODO]
    support/         tickets, SLA, knowledge base, client portal             [TODO]
    assets/          devices, licences, subscriptions                        [TODO]
    analytics/       dashboards, ML risk scores, forecasts, exports          [TODO]
frontend/
  src/features/<module>/   small files: pages, components, hooks, api, types
  src/lib/api.ts           API helpers
  src/app/router.tsx       routes
  src/components/layout/app-shell.tsx   navigation
docs/                SPEC.md, API.md, ERD.md, DEPLOYMENT.md
docker-compose.yml, README.md, PROGRESS.md, AGENTS.md
```

### 3.2 Backend conventions

- One Django app per module under `backend/apps/<module>/` with `models.py`, `serializers.py`, `views.py`, `services.py`, `permissions.py`, `urls.py`, `tests/`.
- All models inherit `AuditedModel` from `apps.core.models` (timestamps, created_by/updated_by, soft delete where applicable).
- Business logic lives in `services.py`, not in views or serializers.
- New apps are added to `INSTALLED_APPS` in `config/settings/base.py` and mounted in `backend/config/urls.py` under `/api/v1/`.
- REST API is versioned (`/api/v1/`), paginated, filterable, searchable, and orderable. OpenAPI docs are generated by drf-spectacular.
- Money uses `Decimal` (never float), with one base currency configurable in company settings. Datetimes are timezone-aware.
- Multi-step writes (invoice creation, payroll runs, leave approval, payment allocation) run inside `transaction.atomic`.
- Avoid N+1 queries (`select_related` / `prefetch_related`). Add DB indexes on foreign keys and common filters.
- Scheduled work uses django-q2. Follow the existing pattern (the `accrue_leave_balances` management command).

### 3.3 Frontend conventions

- Feature code in `frontend/src/features/<module>/`, split into **small files**. Do not add to the oversized legacy pages (`hr-page.tsx`, `projects-page.tsx`); create new files instead.
- Server state with TanStack Query. Forms with react-hook-form + zod.
- Every page has loading (skeleton), empty, and error states. Toast feedback for mutations.
- Accessible controls (labels, focus management, keyboard support), responsive layout, dark and light themes.
- Professional SaaS-quality UI: consistent spacing and typography, no unstyled default components.

### 3.4 Shared data (what makes this an ERP)

Modules must share data through foreign keys, not duplicate it:

```
User -> Employee -> Department
Client -> Project -> Task -> TimeEntry -> InvoiceLine -> Invoice -> Payment
Lead -> Deal -> Quote -> (won) Client + Project
Employee -> SalaryStructure -> PayrollRun -> Payslip
Expense / VendorBill / Invoice / Payment / Payroll -> LedgerEntry
Client -> Ticket ; Employee -> Asset assignment
```

Every change to a business record is written to the audit log.

### 3.5 Security

- Role-based access control, enforced on the backend for every endpoint, plus object-level rules (employees see their own payslips, timesheets and leave; managers see their team; finance data restricted to Finance/Admin; clients see only their own portal data).
- Roles: Admin, HR, Manager, Finance, Sales, Support, Employee, Client (portal). Use the role definitions in `apps.core`.
- Validate all input. Validate uploads (type, size). Rate-limit authentication endpoints. No secrets in code. CSRF and CORS configured correctly. Audit-log sensitive actions (role changes, payroll approval, invoice status changes, exports).

## 4. Quality bar

- Backend coverage at least 80% (`--cov-fail-under=80`). The most rigorous tests cover money logic (invoicing, payroll, ledger balancing, tax, rounding, zero and negative amounts, double-invoicing prevention) and permissions (cross-role access denial).
- Every list endpoint has pagination, filtering, and tests. Every form validates with helpful messages.
- Type hints throughout Python; strict TypeScript. No unused code. Never weaken or delete a test to make it pass.
- CI (GitHub Actions) runs lint, type checks, and tests on every push.
- Checks that must pass before any work counts as done:
  - Backend (from `/backend`): `python -m ruff check .`, `python -m ruff format --check .`, `python -m mypy apps config`, `python -m pytest --cov=apps --cov-fail-under=80`
  - Frontend (from `/frontend`): `npm run lint`, `npx tsc -b`, `npm test`, `npm run build`

## 5. Documentation deliverables

## 6. Delivery order

Work in small slices, one at a time, in the order listed in `PROGRESS.md`. Do not start a new slice until the current one passes all checks and is committed.

## 7. Backlog (after the slices in PROGRESS.md)

HR extras (onboarding/offboarding checklists, performance reviews and OKRs, training, announcements, self-service portal), email log, sales forecast analytics, maintenance logs, CSV/Excel import on list pages, session management.

## 8. Definition of done (every slice)

Tests and linters green, app starts with one command, new features reachable from the UI, permissions verified per role, `docs/API.md` and `PROGRESS.md` updated, work committed.
